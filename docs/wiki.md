## 1. PRD (POC)
Prove the path: harmless photo from an Android phone -> durable upload -> generic Web Push to a subscribed iPhone Home Screen PWA -> exact private result behind login; parent inbox is the fallback. Out of scope: AI, journal scoring, Google sessions, Family Link.
Acceptance (local, automated): see section 6. Acceptance (device, **untested**): section 8.

## 2. Architecture
One Heroku web dyno (Node 22, Express 5) + one Postgres. No S3/Redis/worker. Heroku filesystem is non-durable; nothing is written to disk.
- `src/config.js` env config; `db.js` seam over `pg` (prod) / PGlite (tests) + SQL migrations; `security.js` scrypt, token hashing; `images.js` validate+re-encode; `push.js` endpoint validation + web-push; `dispatch.js` claim/send/record; `app.js` routes; `public/` PWA (manifest, `sw.js`, vanilla JS).
- Tables: families, users(role uploader|parent1|parent2), sessions(token_hash), uploads(image bytea, idempotency_key unique per family, expires_at), subscriptions(endpoint unique, session_hash), sends(unique(upload, subscription), status).
- Flow: upload -> validate bytes/pixels/format -> re-encode (no metadata) -> one transaction saves upload + `pending` send rows -> commit -> parallel bounded (8 s) inline sends -> each row set to accepted_by_push_service | failed | unknown | disabled_endpoint. No automatic retry; manual resend.
- Statuses never claim delivered/read. `unknown` (timeout) resend requires explicit duplicate confirmation.
- Payload: `{v:1,title:'New upload ready',id:<uuid>}` only. SW shows generic text; click opens `/uploads/<id>` (id regex-validated, same-origin by construction); logged-out users go to `/login?next=...` and return (next validated as a same-origin path).

## 3. Conventions
Folders: `src/ public/ migrations/ scripts/ test/ docs/`. ES modules. Errors: generic JSON `{error:code}`; logs carry error class/status only, never endpoints, keys, tokens or image bytes. Config via env only. Branches `task/<name>`, one writer per worktree, no remote writes without approval. No status-only commits.

## 4. Security decisions (summary)
Session cookie HttpOnly, Secure, **SameSite=Lax** (Strict would drop the cookie on notification-tap navigation); mutations require `X-STM-Request: 1` + same-host Origin. Token: 32 random bytes, SHA-256 stored, 30-day expiry, new token per login. Passwords scrypt + per-user salt + timingSafeEqual; unknown-user path does equal work. Login backoff per user and per IP (in memory, single dyno). Every resource is family-scoped; uploader sees only own uploads and never image bytes; image bytea selected only in the image route. CSP `default-src 'self'`, nosniff, frame-ancestors none, Referrer-Policy no-referrer, API `Cache-Control: no-store`. SW caches nothing. Endpoints: exact-host allowlist (`web.push.apple.com`, `fcm.googleapis.com`), https, canonical form, no userinfo/port, validated at registration (no fetch) and before every send; web-push does not follow redirects. Limits: 10 MB raw, 25 MP decoded (header-checked before decode), JPEG/PNG/WebP only, output JPEG <=2 MB, edge <=1600, EXIF/GPS dropped, TTL 7 days with request-time cleanup.

## 5. ADRs
**ADR-001 Single service + single Postgres (accepted).** Context: POC, minimal ops. Options: S3 + worker; DB-only. Decision: DB-only, bytea <=2 MB. Consequences: DB growth bounded by 7-day TTL; revisit for the real product.
**ADR-002 Own sessions + scrypt instead of express-session (accepted, senior-reviewed).** Fewer dependencies; hashed tokens.
**ADR-003 SameSite=Lax + header/Origin CSRF (accepted, senior change).** Reason: iOS notification-tap navigation.
**ADR-004 Inline bounded push, persisted intents, manual recovery (accepted).** No queue; Heroku 30 s request limit respected by parallel 8 s sends. Dyno death leaves rows `pending` (visible as needing attention).
**ADR-005 Exact-host push endpoint allowlist (accepted, reviewer).** Prevents SSRF via forged subscriptions. Consequence: other push services (e.g. Mozilla) are rejected until added via `ALLOWED_PUSH_HOSTS`.
**ADR-007 Subscription rebind retires old binding (accepted, reviewer P1 2026-10-30).** If an endpoint is registered by a different user (account switch or other family), the old subscription row and its send history are deleted and a new subscription identity is created in one transaction; dispatch also re-checks that recipient and upload share a family. Same-user re-registration updates in place. Consequence: history of past sends for that endpoint is lost on switch.
**ADR-008 Permission prompt first in the tap (accepted, reviewer P2).** `public/push-enable.js` calls `Notification.requestPermission()` before any awaited SW setup so it stays inside transient user activation; SW registration happens after a grant. Real iPhone behavior still untested.
**ADR-009 Enforce HTTPS in the app (accepted, reviewer P1/P2 + project-lead spec, 2026-10-30; found on live release v5).** Heroku does not redirect http itself. First middleware (before body parsing and all handlers): a request counts as https only if every `X-Forwarded-Proto` value is exactly `https`; any `http`, unknown or mixed/duplicate-with-http chain is insecure (ambiguous schemes are rejected). GET/HEAD over insecure -> 308 to the validated canonical `APP_ORIGIN` only (https, plain host, 443-only: no explicit port of any kind, no userinfo/path/query/fragment; parsed with the native URL parser and the input must equal its own origin); the request Host is never used. Every other method, and every GET when `APP_ORIGIN` is invalid, -> 426 unread (never redirected or replayed, so credentials are not parsed or processed). HSTS only on https. Startup fails closed in production if `APP_ORIGIN` is missing or invalid. `INSECURE_COOKIES=1` (local dev) disables enforcement. **Limit:** Heroku's routing docs say forwarded headers should not be trusted for security, so these checks are defense in depth; the router's real behavior against a spoofed `X-Forwarded-Proto: https` over plain http is unverified until a live curl after the approved redeploy (result recorded below).
**Live observation on release v7 (2026-10-30, developer and independent reviewer):** over plain http, a singleton spoofed `X-Forwarded-Proto: https` got 308 on GET and 426 on POST; mixed chains (`https, http`, `http, https`, `garbage, https`) got 308 on GET and 426 on POST; raw duplicated header lines (both orders, and `https`+`https`) over http gave 308 on GET and 426 on empty POST; http GET/HEAD got 308 to the canonical origin; no Set-Cookie on any of these. HTTPS responses returned 200/401 with `Strict-Transport-Security: max-age=15552000`. A foreign Host over http is answered by Heroku's router (404) before reaching the app. **Established:** spoofed-http requests did not bypass enforcement. **Not established:** whether the router overwrites or appends `X-Forwarded-Proto`, because the header value received by the app was not observed; no inference is made.
**ADR-006 Supersedes the Family Link local POC (2026-10-29).** The local Family Link POC folder is preserved and stopped; Heroku hosting is required and no parent Google session moves to the cloud.

**Accepted POC limitations (senior and project-lead review 2026-10-30):**
- Logout (and account switch) deletes the browser's subscription rows, which cascades to delete that subscription's send history for past uploads.
- Per-username login backoff means anyone who knows a username can lock that account out for up to 15 minutes. Accepted for the POC. The throttle map is in memory (single dyno), pruned, and capped at 5000 entries by evicting the oldest entries (not clearing).
- No storage quota: Essential-tier Postgres holds roughly 500 uploads of 2 MB; the 7-day TTL covers normal use.
- `rejectUnauthorized:false` for Heroku Postgres TLS is the Heroku-standard setting (accepted ADR item).
- The upload idempotency key persists in the page across failed/lost-response retries and resets on success or choosing a different file. It lives in page memory only, so a full reload during a lost response starts a new key (duplicate possible; accepted).

## 10. PRD: journal MVP (JRN-1)
**Outcome.** The child uploads one photo of one English handwritten page. A model reads it literally; the server counts words deterministically and suggests screen time; parents see the photo, the literal text, the count and a suggestion, can correct the text, and decide the final time themselves in Family Link. The child sees only a coarse status. Suggestions are independent per upload and never cumulative.

| Words (count_v1) | Suggested minutes |
|---:|---:|
| 0-49 | 0 |
| 50-99 | 45 |
| 100-149 | 60 |
| 150+ | 75 |

**Out of scope (deliberately):** writing feedback, grading, a daily ledger or day grouping, automatic Family Link control, a second provider or automatic model fallback, multi-page submissions, extra worker or Heroku app, Redis.

**count_v1** (whole transcript, headings included): curly apostrophes are normalized; en/em dashes and slashes separate words; a word is `[A-Za-z]+(?:['-][A-Za-z]+)*`; digits, punctuation and `[?]` count zero; names and misspellings count; non-ASCII letters act as separators (pinned by tests, e.g. `résumé` = 2). Tiers live in one function, tested at 0, 49, 50, 99, 100, 149, 150.

**Review rule (fixed).** An analysis is `needs_review` (suggestion shown as provisional) if the transcript has any `[?]`, the model reports any page issue, the transcript has no words, or the count is within 5 words of 50, 100 or 150. Otherwise it is `ready`. A blank or unreadable page can never become a confidently complete zero. A parent correction recomputes the count with the same rule and keeps only the advisory flags (empty, near-threshold).

## 11. Design: journal MVP
**Data (migration 002).** `journal_analyses` (one per upload, cascades with the upload's 7-day expiry): status queued/processing/ready/needs_review/failed, `attempts` (0-2, enforced by a CHECK), `round`, `attempt_token`, `lease_until`, model/prompt/count versions, original transcript, word count, suggestion, flags, and separate `corrected_*` columns plus `version` for optimistic concurrency. `ai_budget_months` holds only a per-UTC-month reserved amount (no journal content, so it can outlive uploads). `job_slot` is a one-row lease that enforces concurrency one. `sends` gained `round`; its unique key is now (upload, subscription, round).

**Flow.** Upload validates and re-encodes (long edge <= 1568), then in one transaction inserts the upload and a `queued` analysis (after a per-family daily cap check under a family row lock) and returns 201 immediately with no push. After the response the same process claims the job: in one transaction it takes the slot lease, reserves worst-case cost in the month row (compare-and-add against the USD 5 cap), increments `attempts`, and stores a fresh random attempt token. Only then does it call Anthropic (forced single tool, inline base64 image, 45 s timeout, no SDK so no hidden retries). Completion, failure, and the creation of notice intents are one transaction, each conditional on the current attempt token and an unexpired upload. A minute sweep (and once at startup) requeues expired leases while attempts remain, otherwise fails them with a notice.

**Attempts.** Two total per analysis, including manual retries. A transient failure (timeout, network, 429, 5xx, schema-invalid output) gets the one automatic re-attempt; refusals and truncation do not. After two attempts the parent can no longer retry; they still have the photo.

**Notices.** One generic push per upload per round, after a terminal state (ready, needs_review, or failed once permitted attempts are exhausted). No push for a temporary failure. The payload is unchanged from the POC: `{v, title, id}`, no text or minutes. A manual retry that reaches a new terminal state starts round 1 and creates its own notice (the unique key includes the round, so it is not swallowed by the round-0 row). Corrections do not push. Push failure leaves inbox and result usable; the existing resend re-sends the notice, never the API request.

**Budget.** Fixed conservative reservation per permitted call = 2x worst case, where worst case = (input-token bound x input price + max output tokens x output price). Input bound = text/2 + 3136 image tokens + slack (about 4,091); output max 4096; Haiku 5.5 prices from the official page (USD 0.10 / 0.50 per million tokens, prompts up to 100,000 tokens). The model, prices and bounds must validate before any dispatch; an unpriced model, bad bounds, a cap smaller than one reservation, or timeout >= lease disables dispatch. Reservations are never refunded, so ambiguous outcomes stay charged. This is an app-side planning ceiling, not a provider-enforced hard cap; a provider console limit is an additional backstop if available. No per-page price is promised before a measured request.

## 12. ADRs: journal MVP
**ADR-010 In-process durable jobs on the existing web dyno (accepted; senior pre-plan, 2026-10-30).** Options: separate worker dyno, external queue, DB-backed claims in the web process. Decision: DB-backed claims, no new infrastructure. Consequence: a dyno restart can interrupt a job; the lease sweep recovers it within the two-attempt limit.
**ADR-011 Concurrency one via a single-row lease (accepted).** `job_slot` is claimed in the same transaction as the attempt increment and the budget reservation, so startup, sweep and request claimers cannot overlap. A client-side timeout does not prove the provider stopped, so the slot is held until the lease (90 s) expires and reservations are never released.
**ADR-012 Attempt-token fencing (accepted; reviewer invariant).** Every completion, failure and notice-creating write is conditional on `attempt_token` and an unexpired upload, so an old attempt finishing late cannot overwrite a later one, recreate expired data, or notify.
**ADR-013 Fixed worst-case reservation, not token-exact accounting (accepted; senior).** Simpler and safe. Cost: the ceiling is conservative (2x) and counts failed calls.
**ADR-014 Server-side deterministic count; model returns data only (accepted).** Strict schema via a forced tool; any deviation is a failure, never a partial result. Review flags come from observable signals, not model confidence.
**ADR-015 Single correction slot with optimistic version check (accepted; senior).** One `corrected_*` set, overwriting only itself, so the original is always preserved; a stale version returns 409. Corrections never extend the upload's expiry.
**ADR-016 Notice key includes a round (accepted; reviewer).** Needed so a manual recovery notification is not lost behind the POC's unique upload/subscription row.
**ADR-017 Model is configuration, price gate is code (accepted).** `ANTHROPIC_MODEL` defaults to `claude-haiku-5-5`; a model with no entry in the price table can never be dispatched, so changing the model needs a reviewed price entry. No automatic escalation to a larger model.
**Superseded by scope cuts (kept for history):** the earlier draft's revisions table, parent decision/ledger records, daily grouping and writing feedback were removed from the MVP (see the room design document's superseded section).
