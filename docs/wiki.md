## 1. PRD (POC)
Prove the path: harmless photo from an Android phone -> durable upload -> generic Web Push to a subscribed iPhone Home Screen PWA -> exact private result behind login; parent inbox is the fallback. Out of scope: AI, journal scoring, Google sessions, Family Link.
Acceptance (local, automated): see section 6. Acceptance (device): section 8 (the happy path was later observed by the owner on real devices; the negative cases remain untested - see section 14).

## 2. Architecture
One Heroku web dyno (Node 22, Express 5) + one Postgres. No S3/Redis/worker. Heroku filesystem is non-durable; nothing is written to disk.
- `src/config.js` env config; `db.js` seam over `pg` (prod) / PGlite (tests) + SQL migrations; `security.js` scrypt, token hashing; `images.js` validate+re-encode; `push.js` endpoint validation + web-push; `dispatch.js` claim/send/record; `app.js` routes; `public/` PWA (manifest, `sw.js`, vanilla JS).
- Tables: families, users(role uploader|parent1|parent2), sessions(token_hash), uploads(image bytea, idempotency_key unique per family, expires_at), subscriptions(endpoint unique, session_hash), sends(unique(upload, subscription), status).
- Flow: upload -> validate bytes/pixels/format -> re-encode (no metadata) -> one transaction saves upload + `pending` send rows -> commit -> parallel bounded (8 s) inline sends -> each row set to accepted_by_push_service | failed | unknown | disabled_endpoint. No automatic retry; manual resend.
- Statuses never claim delivered/read. `unknown` (timeout) resend requires explicit duplicate confirmation.
- Payload: `{v:1,title:'New upload ready',id:<uuid>}` only. SW shows generic text; click opens `/uploads/<id>` (id regex-validated, same-origin by construction); logged-out users go to `/login?next=...` and return (next validated as a same-origin path).

## 3. Conventions
Folders: `src/ public/ migrations/ scripts/ test/ docs/`. ES modules. Errors: generic JSON `{error:code}`; logs carry error class/status only, never endpoints, keys, tokens or image bytes. Config via env only. Branches `task/<name>`, one writer per worktree, no remote writes without approval. No status-only commits.

## 4. Security decisions (summary)
Session cookie HttpOnly, Secure, **SameSite=Lax** (Strict would drop the cookie on notification-tap navigation); mutations require `X-STM-Request: 1` + same-host Origin. Token: 32 random bytes, SHA-256 stored, 30-day expiry, new token per login. Passwords scrypt + per-user salt + timingSafeEqual; unknown-user path does equal work. Login backoff per user and per IP (in memory, single dyno). Every resource is family-scoped; uploader sees only own uploads and never image bytes; image bytea selected only in the image route. CSP `default-src 'self'`, nosniff, frame-ancestors none, Referrer-Policy no-referrer, API `Cache-Control: no-store`. SW caches nothing. Endpoints: exact-host allowlist (`web.push.apple.com`, `fcm.googleapis.com`), https, canonical form, no userinfo/port, validated at registration (no fetch) and before every send; web-push does not follow redirects. Limits: 10 MB raw, 25 MP decoded (header-checked before decode), JPEG/PNG/WebP only, output JPEG <=2 MB, edge <=1600, EXIF/GPS dropped, TTL 7 days with request-time cleanup.

## 5. ADRs
**ADR-001 Single service + single Postgres (accepted).** Context: POC, minimal ops. Options: S3 + worker; DB-only. Decision: DB-only, bytea <=2 MB. Consequences: DB growth bounded by 7-day TTL; revisit for the real product.
**ADR-002 Own sessions + scrypt instead of express-session (accepted, senior-reviewed).** Fewer dependencies; hashed tokens.
**ADR-003 SameSite=Lax + header/Origin CSRF (accepted, senior change).** Reason: iOS notification-tap navigation.
**ADR-004 Inline bounded push, persisted intents, manual recovery (accepted).** No queue; Heroku 30 s request limit respected by parallel 8 s sends. Dyno death leaves rows `pending` (visible as needing attention).
**ADR-005 Exact-host push endpoint allowlist (accepted, reviewer).** Prevents SSRF via forged subscriptions. Consequence: other push services (e.g. Mozilla) are rejected until added via `ALLOWED_PUSH_HOSTS`.
**ADR-007 Subscription rebind retires old binding (accepted, reviewer P1 2026-10-30).** If an endpoint is registered by a different user (account switch or other family), the old subscription row and its send history are deleted and a new subscription identity is created in one transaction; dispatch also re-checks that recipient and upload share a family. Same-user re-registration updates in place. Consequence: history of past sends for that endpoint is lost on switch.
**ADR-008 Permission prompt first in the tap (accepted, reviewer P2).** `public/push-enable.js` calls `Notification.requestPermission()` before any awaited SW setup so it stays inside transient user activation; SW registration happens after a grant. Real iPhone behavior still untested.
**ADR-009 Enforce HTTPS in the app (accepted, reviewer P1/P2 + project-lead spec, 2026-10-30; found on live release v5).** Heroku does not redirect http itself. First middleware (before body parsing and all handlers): a request counts as https only if every `X-Forwarded-Proto` value is exactly `https`; any `http`, unknown or mixed/duplicate-with-http chain is insecure (ambiguous schemes are rejected). GET/HEAD over insecure -> 308 to the validated canonical `APP_ORIGIN` only (https, plain host, 443-only: no explicit port of any kind, no userinfo/path/query/fragment; parsed with the native URL parser and the input must equal its own origin); the request Host is never used. Every other method, and every GET when `APP_ORIGIN` is invalid, -> 426 unread (never redirected or replayed, so credentials are not parsed or processed). HSTS only on https. Startup fails closed in production if `APP_ORIGIN` is missing or invalid. `INSECURE_COOKIES=1` (local dev) disables enforcement. **Limit:** Heroku's routing docs say forwarded headers should not be trusted for security, so these checks are defense in depth; the router's real behavior against a spoofed `X-Forwarded-Proto: https` over plain http is unverified until a live curl after the approved redeploy (result recorded below).
**Live observation on release v7 (2026-10-30, developer and independent reviewer):** over plain http, a singleton spoofed `X-Forwarded-Proto: https` got 308 on GET and 426 on POST; mixed chains (`https, http`, `http, https`, `garbage, https`) got 308 on GET and 426 on POST; raw duplicated header lines (both orders, and `https`+`https`) over http gave 308 on GET and 426 on empty POST; http GET/HEAD got 308 to the canonical origin; no Set-Cookie on any of these. HTTPS responses returned 200/401 with `Strict-Transport-Security: max-age=15552000`. A foreign Host over http is answered by Heroku's router (404) before reaching the app. **Established:** spoofed-http requests did not bypass enforcement. **Not established:** whether the router overwrites or appends `X-Forwarded-Proto`, because the header value received by the app was not observed; no inference is made.
**ADR-006 Supersedes the Family Link local POC (2026-10-29).** The local Family Link POC folder is preserved and stopped; Heroku hosting is required and no parent Google session moves to the cloud.

**Accepted POC limitations (senior and project-lead review 2026-10-30):**
- Logout (and account switch) deletes the browser's subscription rows, which cascades to delete that subscription's send history for past uploads.
- Per-username login backoff means anyone who knows a username can lock that account out for up to 15 minutes. Accepted for the POC. The throttle map is in memory (single dyno), pruned, and capped at 5000 entries by evicting the oldest entries (not clearing).
- No storage quota: Essential-tier Postgres holds roughly 500 uploads of 2 MB; the 7-day TTL covers normal use.
- `rejectUnauthorized:false` for Heroku Postgres TLS is the Heroku-standard setting (accepted ADR item).
- The upload idempotency key persists in the page across failed/lost-response retries and resets on success or choosing a different file. It lives in page memory only, so a full reload during a lost response starts a new key (duplicate possible; accepted).

## 7. Run / deploy / rollback
**Seeding users (private, run by the parent after HTTPS is verified live):** `node scripts/seed-local.js` from the repo root on the parent's own Mac (needs `npm ci` and a logged-in Heroku CLI). It prompts with hidden input for 3 passwords (12-200 chars, the same rule login enforces; distinct; confirmed), hashes them locally with the app's scrypt format, and pipes ONLY the hashes as JSON over stdin to `heroku run -a <app> node scripts/seed-hashed.js` (the `APP` constant at the top of `scripts/seed-local.js` names the Heroku app; set it to yours). Passwords never appear in argv, env, files, shell history, Heroku command metadata or chat. `--dry-run` hashes and validates without sending. The server side validates the hash format, refuses if any family exists, and inserts atomically. Terminal state is restored on exit, SIGINT, SIGTERM and SIGHUP. Not run yet.

## 10. PRD: journal MVP (JRN-1)
**Outcome.** The child uploads one photo of one English handwritten page. A model reads it literally; the server counts words deterministically and suggests screen time; parents see the photo, the literal text, the count and a suggestion, can correct the text, and decide the final time themselves in Family Link. The child sees only a coarse status. Suggestions are independent per upload and never cumulative.

| Words (count_v1) | Suggested minutes |
|---:|---:|
| 0-49 | 0 |
| 50-99 | 45 |
| 100-149 | 60 |
| 150+ | 75 |

**Out of scope (deliberately):** writing feedback, grading, a daily ledger or day grouping, automatic Family Link control, a second provider or automatic model fallback, multi-page submissions, extra worker or Heroku app, Redis.

**count_v1** (whole transcript, headings included): curly apostrophes are normalized; en/em dashes and slashes separate words; a word is `[A-Za-z]+(?:['-][A-Za-z]+)*`; digits, punctuation and `[?]` count zero; names and misspellings count; non-ASCII letters act as separators (pinned by tests, e.g. `résumé` = 2). Tiers live in one function, tested at 0, 49, 50, 99, 100, 149, 150.

**Review rule (fixed).** An analysis is `needs_review` (suggestion shown as provisional) if the transcript has any `[?]`, the model reports any page issue, the transcript has no words, or the count is within 5 words of 50, 100 or 150. Otherwise it is `ready`. A blank or unreadable page can never become a confidently complete zero. A parent correction recomputes the count with the same rule and keeps only the advisory flags (empty, near-threshold).

## 11. Design: journal MVP
**Data (migration 002).** `journal_analyses` (one per upload, cascades with the upload's 7-day expiry): status queued/processing/ready/needs_review/failed, `attempts` (0-2, enforced by a CHECK), `attempt_token`, `lease_until`, model/prompt/count versions, original transcript, word count, suggestion, flags, and separate `corrected_*` columns plus `version` for optimistic concurrency. `ai_budget_months` holds only a per-UTC-month reserved amount (no journal content, so it can outlive uploads). `job_slot` is a one-row lease that enforces concurrency one. The existing `sends` table and its unique (upload, subscription) key are unchanged.

**Flow.** Upload validates and re-encodes (long edge <= 1568), then in one transaction inserts the upload and a `queued` analysis (after a per-family daily cap check under a family row lock) and returns 201 immediately with no push. After the response the same process claims the job: in one transaction it takes the slot lease, reserves worst-case cost in the month row (compare-and-add against the USD 5 cap), increments `attempts`, and stores a fresh random attempt token. Only then does it call Anthropic (forced single tool, inline base64 image, 45 s timeout, no SDK so no hidden retries). Completion, failure, and the creation of notice intents are one transaction, each conditional on the current attempt token and an unexpired upload. A minute sweep (and once at startup) requeues expired leases while attempts remain, otherwise fails them with a notice.

**Attempts.** Two automatic attempts at most per analysis, and **no post-terminal API retry of any kind** (rule settled 2026-10-31; there is no retry route or button). A transient failure (timeout, network, 429, 5xx, schema-invalid output) gets the one automatic re-attempt; refusals, truncation, 4xx and unusable complete responses do not. After a terminal failure the parent still has the photo, and uploading the page again starts a fresh analysis.

**Slot hold after ambiguous outcomes.** The slot is released immediately only when the provider outcome is KNOWN (success, schema-invalid or otherwise unusable complete response, refusal, truncation, 4xx, or no call made). After a timeout, dropped connection or 429/5xx the provider may still be working, so the slot stays held until its 90 s lease expires; no other job can start a second paid call in that window. If the finishing transaction itself fails on a database error the slot is also held until the lease runs out (acceptable; noted by the senior review).

**One deadline.** The 45 s deadline covers connect, headers, the whole body read and JSON parsing, and is cleared only after the exchange ends. An abort or a body dropped mid-read is a retryable UNKNOWN outcome, not a final bad_response; error statuses abort the connection instead of reading their bodies.

**Duplicate before cap.** Inside the per-family lock, a repeat of an already accepted idempotency key is resolved (200 with the original id) before the daily cap is evaluated, so simultaneous identical uploads give one 201 and one 200 and one row, even at the cap.

**Paused.** If the job runner is not active (AI disabled, no key, unpriced model or invalid limits), queued or processing analyses are reported as `paused`; the inbox and detail view say "Analysis paused; photo available" instead of "Reading". Rows stay queued, nothing is claimed, no call is made and no attempt or reservation is consumed. When AI is re-enabled the same rows are processed and the label reverts. The child still sees only a coarse status.

**Notices.** One generic push per upload, after a terminal state (ready, needs_review, or failed once permitted attempts are exhausted), using the POC's original unique (upload, subscription) row. No push for a temporary failure. The payload is unchanged from the POC: `{v, title, id}`, no text or minutes. Corrections do not push. Push failure leaves inbox and result usable; the existing resend re-sends the notice, never the API request.

**Budget.** Fixed conservative reservation per permitted call = 2x worst case, where worst case = (input-token bound x input price + max output tokens x output price). Input bound = text/2 + 3136 image tokens + slack (about 4,091); output max 4096; Haiku 5.5 prices from the official page (USD 0.10 / 0.50 per million tokens, prompts up to 100,000 tokens). The model, prices and bounds must validate before any dispatch; an unpriced model, bad bounds, a cap smaller than one reservation, or timeout >= lease disables dispatch. Reservations are never refunded, so ambiguous outcomes stay charged. This is an app-side planning ceiling, not a provider-enforced hard cap; a provider console limit is an additional backstop if available. No per-page price is promised before a measured request.

## 12. ADRs: journal MVP
**ADR-010 In-process durable jobs on the existing web dyno (accepted; senior pre-plan, 2026-10-30).** Options: separate worker dyno, external queue, DB-backed claims in the web process. Decision: DB-backed claims, no new infrastructure. Consequence: a dyno restart can interrupt a job; the lease sweep recovers it within the two-attempt limit.
**ADR-011 Concurrency one via a single-row lease (accepted).** `job_slot` is claimed in the same transaction as the attempt increment and the budget reservation, so startup, sweep and request claimers cannot overlap. A client-side timeout does not prove the provider stopped, so the slot is held until the lease (90 s) expires and reservations are never released.
**ADR-012 Attempt-token fencing (accepted; reviewer invariant).** Every completion, failure and notice-creating write is conditional on `attempt_token` and an unexpired upload, so an old attempt finishing late cannot overwrite a later one, recreate expired data, or notify.
**ADR-013 Fixed worst-case reservation, not token-exact accounting (accepted; senior).** Simpler and safe. Cost: the ceiling is conservative (2x) and counts failed calls.
**ADR-014 Server-side deterministic count; model returns data only (accepted).** Strict schema via a forced tool; any deviation is a failure, never a partial result. Review flags come from observable signals, not model confidence.
**ADR-015 Single correction slot with optimistic version check (accepted; senior).** One `corrected_*` set, overwriting only itself, so the original is always preserved; a stale version returns 409. Corrections never extend the upload's expiry.
**ADR-016 Notice key includes a round (SUPERSEDED 2026-10-31).** Introduced so a manual terminal-recovery notification would not be lost behind the POC's unique upload/subscription row. Superseded because the settled MVP rule is no post-terminal API retry: with no manual recovery there is no second terminal state per upload, so the round column, the changed unique key and the retry route were removed (migration 002 edited before any deployment). Kept here for history; revisit only if a retry feature is ever approved.
**ADR-018 Ambiguous outcomes hold the slot through its lease (accepted; reviewer P2, 2026-10-31).** A client-side timeout does not prove the provider stopped. Releasing the slot early let another job start a second paid call while the first might still be running. Known outcomes release immediately.
**ADR-019 One request deadline through the body read (accepted; reviewer P2).** Clearing the timer when headers arrived left a stalled body unbounded and misclassified a dropped body as a final bad response.
**ADR-020 Duplicate resolution before the daily cap, under the family lock (accepted; reviewer P2).** A repeat of an accepted upload is not a new upload and must not be counted or rejected.
**ADR-021 Paused display instead of auto-failing queued jobs (accepted; project-lead decision).** Honest status, no spend, nothing consumed, and processing resumes when AI is re-enabled.
**ADR-017 Model is configuration, price gate is code (accepted).** `ANTHROPIC_MODEL` defaults to `claude-haiku-5-5`; a model with no entry in the price table can never be dispatched, so changing the model needs a reviewed price entry. No automatic escalation to a larger model.
**Superseded by scope cuts (kept for history):** the earlier draft's revisions table, parent decision/ledger records, daily grouping and writing feedback were removed from the MVP (see the room design document's superseded section).

## 15. Black-box integration suite (JRN-BB1)
**Purpose.** Replace the manual app-flow checklist with an automated suite that treats the app as a black box. It runs on every pull request and every push to `main` (GitHub Actions `ci`), and on demand.
**How it works.**
- The real production entry point `node src/server.js` is started as a child process per test, with a clean environment (only `PATH` is inherited, so no real keys reach it) on a loopback port.
- A real PostgreSQL 18 is used: locally a throwaway `postgres:18` Docker container on 127.0.0.1 with tmpfs storage, in CI the job's service container (`BB_PG_URL`). Each test gets its own fresh database. There is no PGlite or in-memory fallback; a wrong major version fails the run.
- External services are faked at the network edge only. The harness starts the server with `node --import test-bb/harness/net-fakes.mjs`, which redirects Anthropic API and Web Push traffic to a per-test fake on 127.0.0.1 and fails closed on any other non-loopback connection; any blocked attempt fails the test. Production never loads this file and nothing in `src/` refers to it. The fake AI reply mirrors the live tool_use shape seen in the owner-run smoke check; the fake push service records encrypted payloads, which the tests decrypt with their own subscription keys (RFC 8291) to prove notifications are generic.
- Browser specs use headless Chromium against the real front end; every browser request to anything but 127.0.0.1 is aborted and fails the test.
- Fixture setup may use SQL (seed users in the documented hash format, precondition expiry or a full monthly budget). Assertions use only HTTP responses, the browser, and what the fake services received. No test imports app, route, job or count code.
- Production timings are not shortened (45 s AI deadline, 90 s lease, 60 s sweep, 20 s retry delay). The slow reliability specs run in parallel; a full run takes about 3 minutes locally.
**Isolation guards (round 1, 2026-11-01).** Every database URL given to the tooling (`BB_PG_URL`, `TEST_DATABASE_URL`) must be a `postgres://` URL to 127.0.0.1, localhost or ::1 with no query parameters; it is checked before any connection, database creation or drop, and `npm run test:all` checks it before the unit suite starts. The egress guard also covers `net.Socket.prototype.connect` (so `new net.Socket().connect`, agents and `tls.connect` are all covered) and UDP sends. Four executable canaries in `test-bb/guards.spec.mjs` run on every suite run: ten outbound APIs refused while loopback works; the guard refuses to load without a 127.0.0.1 fake; non-loopback database URLs refused with the PostgreSQL client never asked to connect; and `test:all` refuses bad URLs before running anything. The first and third canaries fail against the round-0 harness (direct sockets and UDP were not blocked; the client was asked to connect 30 times).
**Coverage (33 scenarios, listed in `test-bb/manifest.json`).** Auth, cookie flags and logout; roles; family isolation; CSRF; AI-off legacy relay (immediate generic push, no journal panel), push 410 disabling a device, failed push keeps the inbox; AI-on: upload returns before analysis and exactly one generic push follows the result; tier boundaries 0/30/49/50/70/99/100/125/149/150/200 with hand-written expectations and review flags; unreadable words, page problems and blank pages force review; literal transcript; parent correction keeps the original and does not extend expiry, concurrent 409, expired upload denial, correction refused while reading; duplicate key in parallel and the daily cap; 5xx retried once; two invalid outputs fail with one push; a hanging provider is cut off and the second attempt waits for the lease; budget ceiling refuses before any call; restart mid-reading recovers once; an expired queued upload is never sent to the AI; HTTPS redirect/426/HSTS and spoofed `X-Forwarded-Proto`; startup fails closed on unsafe `APP_ORIGIN`, and AI stays off without a key; browser flows for child upload, parent inbox, result, correction with original, child status-only view, stale correction rejected with the latest text shown, AI-off view, paused view and recovery, and service-worker registration.
**Run evidence.** A manifest reporter fails the run unless every listed scenario was discovered, ran and passed with none skipped, and prints the totals.
**Not covered, by design.** Real OS push delivery and notification taps (headless Chromium cannot receive real Web Push; tap routing is covered by unit tests), iOS Home Screen behaviour, real AI accuracy, the live Anthropic contract beyond the observed reply shape, and Heroku runtime. GitHub-hosted runners are not network-isolated; the egress guard covers the server process and the browser only.
**Finding recorded by the suite (2026-10-31).** When a parent saves a correction that conflicts with the other parent's, the stale edit is correctly rejected and the latest text is shown, but the "Someone else changed this" message is cleared by the immediate re-render, so it is never visible. The test asserts the actual behaviour; the message fix is a product follow-up.
**Validation helper tests** live on the PR #3 branch and are not on `main`; if that PR is merged they join `npm test` and therefore CI automatically.

## 16. Phase 2: camera-first upload and UI refresh (JRN-P2)
**Scope.** Front end (`public/`), plus one separately authorized server startup fix (a failed `listen` is fatal; see the reliability paragraph below); no schema, dependency or service-worker change. The design document and acceptance were agreed before coding (senior pre-plan and independent acceptance, 2026-11-01).
**Upload flow.** The child's page has a primary "Take photo & upload" button and a secondary "Choose from library" button. Each opens a visually hidden native file input from the tap: the camera input has `accept="image/*" capture="environment"` (a browser hint; some browsers show a picker instead), the library input has no `capture`. A camera photo uploads as soon as it is accepted; a library photo waits for "Upload photo". No custom camera stream is used.
**State (ADR-022).** Upload state lives in `public/upload-flow.js`, outside the view, so re-rendering never loses the photo: one selection is one in-memory File plus one idempotency key. A failed or lost-response attempt keeps both, and "Try again" resends the same photo with the same key without reopening the camera; the server returns the original upload rather than a duplicate. Every deliberate new selection (including the same photo after a success) gets a new key. A cancelled picker changes nothing, so a failed photo stays retryable. One attempt runs at a time, covering both the resize and the network request; actions while busy are ignored and the buttons are disabled. Nothing is persisted: a reload starts over.
**Errors (ADR-023).** Server and network errors are shown in plain language (unsupported photo type, too large, daily limit, signed out, connection). Codes are never shown. Permanent refusals offer "Choose a different photo" instead of "Try again".
**Visual (ADR-024).** Navy primary actions, slate text, off-white background, white bordered cards, status chips; system fonts only. All styling is in `style.css`: the CSP (`default-src 'self'`) blocks inline styles, so none are used (a pre-existing inline style on the correction box had been silently ignored). Controls are at least 44 px tall, focus is visible, fields are labelled, the status area is a live region. The parent detail page shows the photo beside the text on wide screens (760 px and up) and stacked on phones; the photo opens full size.
**Correction conflict fix.** The "Someone else changed this" explanation is now shown after the panel re-renders with the latest text, so it stays visible. This closes the Phase 1 follow-up.
**Tests.** Unit: `test/upload-flow.test.js` (10 tests: camera vs library, cancel, retry keeps key, success clears, same photo again, replacement, single flight, prepare failure, error mapping, no persistence or inline styles). Black-box browser (`test-bb/camera-upload.spec.mjs`, 12 scenarios): input attributes and taps, camera sends exactly one, cancel sends none, library waits for the button, held request blocks taps and new selections, failed request retried with the same key, lost response (server committed, response aborted) returns the same upload as a duplicate, replacement and cancelled replacement, same photo again, plain-language refusal; plus layout at 320 px and 200 % zoom with 44 px controls and keyboard access, desktop side-by-side vs phone stacked, and login styling without CSP violations. The conflict browser test now asserts the explanation is visible.
**Not covered.** The native phone camera itself (permission, shutter, retake) cannot run headless; after deployment the owner checks on Android and iPhone that the camera opens, accepting a photo uploads it, retake or cancel sends nothing, the library path works and a failed upload can be retried without retaking.
**Review round 1 fixes (2026-11-01).** (P1, ADR-025) The upload flow belongs to one signed-in user. Signing out, or any change of user seen by the app, resets it: the photo and key are cleared, an in-flight request is aborted, and an epoch is bumped so that every step after an await (resize, send, late answer) is dropped if the account changed; right before sending, the app also confirms the browser session is still the user who chose the photo. A request already handed to the network before the change may still complete at the server under the previous session; nothing is ever sent under the new one. (P2) A correction that fails on the network keeps the edited text, re-enables Save and explains; no unhandled error. Regressions: 3 unit tests and 6 browser scenarios (selected, failed, preparing with a held resize, sending, B's own upload after the switch, correction network failure).
**Startup and test-port reliability (review round 1, 2026-11-01).** Diagnosis: a one-shot TCP connect probe to 127.0.0.1 after "listening" (not an HTTP health check) captured four refusals with the child alive, no listener on the port at all (lsof), and the same port number in use as the local source port of VPN client connections. Express 5 passes bind errors to the `app.listen` callback, so the server printed "listening" even though it never bound (reproduced in isolation with EADDRINUSE). The ephemeral-port allocation in the harness left a gap in which the OS could hand the number to another connection. The VPN attribution is probable, not proven: the bind errno was not captured at the time. (ADR-026) `src/server.js` now treats a listen error as fatal: logs only the error code, exits 1, never prints the success line or starts jobs; a black-box regression starts the real server on an occupied port. (ADR-027) The harness allocates server ports from per-worker blocks of 400 starting at 20000 (16 workers, 20000-26399), below the OS ephemeral range, and refuses to run if that range overlaps the machine's actual ephemeral range (sysctl on macOS, /proc on Linux). Ports already in use are skipped; exhausting a block fails clearly. Collisions are not impossible (another program may listen there); one now makes the server exit with EADDRINUSE and the test fails. The one-shot TCP probe and its diagnostics stay. No retries or timing changes. The earlier unexplained service-worker failure remains unlinked: its artifact was lost.
**Fake VAPID keys (CI fix, 2026-11-02).** Main CI run 41384287192 failed one black-box scenario: the server refused to start with "Vapid private key should be 32 bytes long when decoded". The test fixture generated fake VAPID keys with Node's ECDH `getPrivateKey()`, which drops leading zero bytes, so about 1 key in 256 was 31 bytes (measured 82 of 20,000). The fixture now left-pads to 32 bytes (private) and 65 bytes (public), as web-push's own generator does, and checks the shape. A guard test pins scalars with one and two leading zero bytes, checks web-push accepts them and that the pair matches, and runs 2,000 random pairs; it fails against the previous fixture. Production keys come from `npm run genvapid` (web-push's generator, already padded) and are unaffected.
